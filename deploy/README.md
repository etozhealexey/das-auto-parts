# Подготовка production

Это шаблоны, а не выполненная выкладка. Сервер, домен и реальный аккаунт менеджера
пользователь пока отложил. VIN и онлайн-оплата также отложены; автоматическое получение
статусов поставщика не подключается по текущему решению.

## Настройка сервера

1. Подготовить Linux-сервер с Python 3.12+, uv, PostgreSQL и nginx. Создать отдельного
   системного пользователя `dasauto`, каталог `/srv/das-auto-parts` и каталог `data/`,
   доступный ему для записи. Исходники устанавливать без `.env`, `data/` и локальных
   резервных копий. Не переносить демо-клиентов из `scripts.seed` в production.
2. Разместить production `.env` с правами 600. Настроить отдельную БД, ключи поставщика,
   плательщика и точку получения. Секреты не передавать в аргументах команд и не печатать.
   Обязательные параметры: `APP_ENV=production`, `DEBUG=false`,
   `SESSION_HTTPS_ONLY=true`, случайный `SECRET_KEY` длиной от 32 символов,
   `ALLOWED_HOSTS=["ваш-домен"]`. Без них production-приложение откажется запускаться.
3. Выполнить `uv sync --locked --no-dev`, затем сделать резервную копию БД и
   `uv run --no-sync alembic upgrade head`. Перед первой публикацией импортировать прайс,
   если он нужен, и проверить дату файла. Не запускать seed с демонстрационными аккаунтами.
4. Установить `das-auto-parts.service`, проверив пути и пользователя. Запуск — один процесс
   Uvicorn на loopback; фоновые циклы работают в нём. Проверить службу через systemd.
5. В `nginx.conf.example` заменить домен и пути сертификатов, выпустить TLS-сертификат,
   выполнить `nginx -t`, затем включить сайт. Прямой порт Uvicorn не публиковать наружу.
6. Проверить HTTPS, вход/выход и атрибут Secure у cookie, главную, каталог,
   `/api/v1/health`, роль менеджера и изоляцию клиентских данных.
   Для тестового оформления оставить `SUPPLIER_ORDERS_ENABLED=false`.
7. Реальную отправку включать только после отдельной проверки бизнес-настроек и явного
   решения владельца. При включении создаются настоящие заказы у поставщика.

## Менеджер

Пользователь сначала регистрируется обычным способом. Назначение роли выполняется
администратором сервера, по конкретному согласованному email:

```sh
uv run --no-sync python -m scripts.set_manager manager@example.com
# Отзыв роли:
uv run --no-sync python -m scripts.set_manager manager@example.com --revoke
```

Это пример адреса. Скрипт не создаёт аккаунты и не меняет пароли. Самостоятельная регистрация
или параметры HTTP-запроса не дают роль. На локальной БД роль реальным пользователям
в рамках текущей задачи не назначалась.

## Резервные копии и обновления

- Регулярно делать `pg_dump -Fc` в закрытый каталог и хранить копии вне сервера приложения.
  Секрет пароля передавать через защищённую настройку PostgreSQL, не через командную строку.
- Перед обновлением сохранить версию кода, копию БД и `.env` отдельно; миграции выполнять
  до запуска новой версии. Для восстановления проверять копию на отдельной БД.
- Журналы: `journalctl -u das-auto-parts`; контролировать HTTP health, свободное место,
  ошибки импорта, дату прайса и неуспешную передачу заказов в кабинете менеджера.
- Откат кода допустим только при совместимой схеме. Платёжный журнал не удалять при откате;
  ошибочные поступления сторнировать. Оплаты в кабинете — ручной учёт, без банковской интеграции.
